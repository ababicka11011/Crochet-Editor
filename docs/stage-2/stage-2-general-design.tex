\section{Architektura systemu}

\subsection{Przegląd logiczny}

Rysunek~\ref{fig:architecture} przedstawia ogólną, logiczną architekturę systemu: główne moduły aplikacji i zależności między nimi, bez odwołań do konkretnych technologii. Strzałki wskazują kierunek wywołań między modułami; moduł wywoływany zwraca wynik do modułu wywołującego. Linia przerywana oznacza dostęp tylko do odczytu.

System składa się z trzech głównych części.

\textbf{Moduł edytora} odpowiada za interakcję z użytkownikiem. Warstwa UI umożliwia edycję i wyświetla schemat, a kontroler koordynuje przepływ informacji między interfejsem a pozostałymi modułami. Kontroler przechowuje także bieżący stan aplikacji i historię operacji (wzoru i układu symboli), dzięki czemu warstwa UI jest odizolowana od logiki dziedzinowej.

\textbf{Model wzoru} przechowuje formalną reprezentację wzoru w postaci grafu oczek wraz z operacjami jego modyfikacji i regułami zapewniającymi, że wzór jest możliwy do wykonania. Stanowi jedyne źródło danych o strukturze wzoru. Zmiany wprowadza wyłącznie kontroler, a moduł algorytmiczny jedynie odczytuje strukturę wzoru.

\textbf{Moduł algorytmiczny} na podstawie struktury wzoru wyznacza układ symboli na schemacie, w tym wstępne położenie nowo dodanych elementów. Komunikuje się z kontrolerem przez wspólny interfejs, co pozwala rozwijać edytor i algorytm niezależnie. W razie potrzeby korzysta z zewnętrznych bibliotek układu grafów. Komunikację z nimi obsługuje adapter, który przygotowuje dane w wymaganym formacie i przekształca wyniki. Dzięki temu zmiana wykorzystywanej biblioteki nie wpływa na pozostałe elementy systemu.

Taki podział oddziela strukturę wzoru od jego reprezentacji graficznej: model opisuje, \emph{co} zostało zaprojektowane, moduł algorytmiczny określa, \emph{jak} przedstawić to na schemacie, a edytor pośredniczy między użytkownikiem a tymi dwoma modułami.

\section{Projekt modułów}

\subsection{Warstwy i zależności}

Architektura jest warstwowa z wyraźnym kierunkiem zależności (warstwy wyższe zależą od niższych, nigdy odwrotnie):

\begin{enumerate}
  \item \textbf{Prezentacja (UI)} -- komponenty React, hooki; zależy wyłącznie od kontrolera.
  \item \textbf{Aplikacja (Kontroler)} -- stan, historia, koordynacja; zależy od modelu wzoru i kontraktu modułu algorytmicznego.
  \item \textbf{Domena (Model wzoru)} -- model wzoru oraz algorytmy rozmieszczania; czysty TypeScript, bez Reacta i DOM; niezależny.
  \item \textbf{Infrastruktura} -- Web Worker, adapter bibliotek, localStorage, File API; implementuje interfejsy zdefiniowane wyżej (odwrócenie zależności).
\end{enumerate}

Struktura modelu wzoru opiera się na grafowej reprezentacji wzorów szydełkowych zaproponowanej przez Seitz i in.~\cite{seitz2022digital, seitz2021language}; jej założenia i wprowadzone zmiany opisano w punkcie~\ref{sec:data-model}.

Kluczowe interfejsy (szkic TypeScript):

\begin{verbatim}
// Domain
interface Stitch {
  id: string;
  type: StitchType;           // sc | hdc | dc | tr | ch | slst | mr ...
  layer: number;
  // ... dodatkowe atrybuty (np. yarn-over count)
}

interface Edge {              // kierunek: od nowszego do starszego węzła
  kind: EdgeKind;             // 'previous' | 'insertion' | 'slip-stitch' | 'surrounding'
  from: StitchId;             
  to: StitchId;
  insertion?: Insertion;      // tylko dla kind = 'insertion'; np. 'both-loops' | 'back-loop' ...
}

interface Pattern  {
  stitches: Record<string, Stitch>;
  edges: readonly Edge[];
  cursor: StitchId | null;    // oczko, z którego wychodzi nić
  currentLayer: number;
  nextOrder: number;          // licznik do nadawania id i kolejności
}

type Result<T> = { ok: true; value: T } | { ok: false; error: string };

interface DomainAPI {
  createNewPattern(start: StartElement): Pattern;
  addStitch(pattern: Pattern, type: StitchType, 
      insertInto?: StitchId | StitchId[],
      insertion?: Insertion): Result<Pattern>;
  removeLastStitch(pattern: Pattern): Result<Pattern>;
  // ... pozostałe operacje z US-01..US-05
  validateInsertion(type: StitchType, target: StitchId): boolean;
}

// Layout
interface StitchPlacement {
  x: number;           // środek symbolu, jednostki modelu
  y: number;
  rotation: number;    // radiany; 0 = podstawa symbolu na dole
  sw: number;          // skala szerokości: W = baseWidth * sw
  sh: number;          // skala wysokości:  H = baseHeight * sh
}

interface Layout {
  placements: Readonly<Record<StitchId, StitchPlacement>>;
  bounds: { minX: number; minY: number; maxX: number; maxY: number };
}

type LayoutResult =
  | { ok: true; layout: Layout; diagnostics: LayoutDiagnostics }
  | { ok: false; error: string };

interface LayoutEngine {
  computeLayout(p: Pattern, options?: LayoutOptions): Promise<LayoutResult>;
}
\end{verbatim}

\subsection{Moduły szczegółowe (katalogi)}

Kod źródłowy jest podzielony na katalogi odpowiadające modułom z rysunku~\ref{fig:architecture}:

\begin{itemize}
  \item \textbf{contracts/} -- typy i interfejsy współdzielone przez moduły, w szczególności kontrakt modułu algorytmicznego. Nie zawiera logiki.
  \item \textbf{model/} -- model wzoru: graf oczek, operacje jego modyfikacji, reguły walidacji oraz katalog rodzajów oczek z ich geometrią.
  \item \textbf{layout/} -- moduł algorytmiczny: wstępne rozmieszczenie nowych oczek, wymienne algorytmy pełnego przeliczenia układu i adaptery zewnętrznych bibliotek.
  \item \textbf{controller/} -- stan aplikacji (wzór i układ), historia operacji, koordynacja wywołań.
  \item \textbf{ui/} -- interfejs użytkownika: obszar schematu, panele i symbole oczek.
  \item \textbf{persist/} -- zapis i odczyt projektu oraz eksport schematu.
\end{itemize}

Katalogi \texttt{model/} i \texttt{layout/} nie zależą od interfejsu użytkownika ani od API przeglądarki, dzięki czemu można je testować niezależnie (por. NFR-M1, NFR-M3), a wymiana biblioteki układu grafów wymaga zmian wyłącznie w module algorytmicznym.

\section{Komunikacja}

Aplikacja działa w całości po stronie klienta, dlatego nie występują w niej protokoły sieciowe ani komunikacja z serwerem. Komunikacja między modułami przebiega następująco:

\begin{itemize}
  \item \textbf{UI $\leftrightarrow$ Kontroler} -- UI przekazuje akcje użytkownika do kontrolera, a komponenty subskrybują wybrane fragmenty stanu. Zmiana stanu powoduje ponowne wyrenderowanie wyłącznie komponentów, których dotyczy.
  \item \textbf{Kontroler $\leftrightarrow$ Model wzoru} -- synchroniczne wywołania czystych funkcji. Każda operacja zwraca nową wersję wzoru albo opis błędu; nowa wersja wraz z układem symboli trafia do historii operacji.
  \item \textbf{Kontroler $\leftrightarrow$ Moduł algorytmiczny} -- dwa tryby:
  \begin{itemize}
    \item \emph{wstępne rozmieszczenie} nowo dodanych oczek -- synchroniczne wywołanie w głównym wątku po każdej zmianie wzoru, bez zmiany położenia pozostałych symboli,
    \item \emph{pełne przeliczenie układu} -- na żądanie użytkownika, asynchronicznie w osobnym wątku (Web Worker). Kontroler wysyła komunikat (\texttt{postMessage}) z wzorem, poprzednim układem i parametrami obliczeń, a wątek zwraca \texttt{LayoutResult}. Każde żądanie ma identyfikator; odpowiedzi na żądania nieaktualne lub anulowane są pomijane. W czasie obliczeń interfejs pozostaje responsywny (NFR-P3).
  \end{itemize}
  \item \textbf{Adapter $\leftrightarrow$ biblioteka zewnętrzna} -- wywołania API wybranej biblioteki układu grafów wewnątrz wątku obliczeniowego, z konwersją danych w obu kierunkach.
  \item \textbf{Zapis i odczyt} -- projekt (wzór i układ) jest zapisywany do pliku pobieranego przez przeglądarkę i wczytywany przez standardowe okno wyboru pliku; w przeglądarkach, które to obsługują, można dodatkowo użyć File System Access API. Autozapis do pamięci lokalnej przeglądarki co najwyżej co 30~s (NFR-R3).
\end{itemize}

Do komunikacji wykorzystywane są wyłącznie mechanizmy wbudowane w przeglądarkę: API Web Workerów i algorytm structured clone przy przesyłaniu danych między wątkami.

\section{Projekt szczegółowy: model danych i zachowanie systemu}

\subsection{Model danych (Domena)}
\label{sec:data-model}

Wzór jest reprezentowany jako graf skierowany. Węzły odpowiadają punktom wbicia -- najczęściej oczkom, ale także otworom, w które można wbić kolejne oczka. Krawędzie są skierowane od węzła nowszego do starszego i należą do jednego z czterech rodzajów: \emph{previous} (skąd wychodzi nić), \emph{insertion} (w co oczko jest wbite, wraz ze sposobem wbicia), \emph{slip-stitch} (oczko ścisłe) oraz \emph{surrounding} (połączenie otworu z oczkami na jego brzegu). Wzór przechowuje również pozycję nici (kursor) i numer bieżącej warstwy. Układ symboli nie jest częścią modelu -- wyznacza go moduł algorytmiczny.

Model danych został oparty na grafowej reprezentacji wzorów szydełkowych zaproponowanej przez Seitz i in.~\cite{seitz2022digital, seitz2021language}. Przejęto z niej podstawowe założenia: węzły grafu odpowiadają punktom wbicia, a nie bezpośrednio oczkom; krawędzie opisują pochodzenie nici (\emph{previous}), wbicie oczka (\emph{insertion}) i oczko ścisłe (\emph{slip-stitch}); otwory w robótce są reprezentowane jako osobne węzły połączone z oczkami na ich brzegu; rzędy i okrążenia są ujednolicone w pojęcie warstwy, a sposób wbicia (np. tylko pod tylną nitkę) jest właściwością krawędzi wbicia.

W stosunku do rozwiązania autorów wprowadzono następujące zmiany:
\begin{itemize}
  \item informacje o połączeniach między oczkami są przechowywane wyłącznie w krawędziach, bez powielania ich w węzłach,
  \item model nie zawiera informacji o położeniu symboli -- układ jest wyznaczany i przechowywany oddzielnie przez moduł algorytmiczny,
  \item każde oczko ma numer porządkowy, a wzór przechowuje bieżącą pozycję nici, co upraszcza operacje edycji.
\end{itemize}

\subsection{Aktywność: dodanie oczka (US-02)}

\begin{enumerate}
  \item Użytkownik wybiera rodzaj oczka z palety.
  \item Użytkownik klika punkt wbicia na schemacie; UI przekazuje akcję do kontrolera.
  \item Kontroler wywołuje operację modelu \texttt{addStitch}, która sprawdza poprawność wbicia.
  \item Jeśli operacja się nie powiedzie, UI wyświetla komunikat z przyczyną, a wzór pozostaje bez zmian.
  \item W przeciwnym razie kontroler wywołuje \texttt{placeNewStitches}, które wyznacza położenie nowego oczka bez zmiany położenia pozostałych.
  \item Kontroler zapisuje nową parę wzór + układ w historii operacji i oznacza układ jako nieaktualny.
  \item UI wyświetla nowe oczko na schemacie.
\end{enumerate}

\subsection{Kluczowe interakcje}

\begin{itemize}
  \item Kliknięcie symbolu w palecie + kliknięcie na schemacie = dodanie oczka (US-02).
  \item Kółko myszy / przyciski +/– = zoom względem kursora (US-07).
  \item Przeciąganie tła = pan.
  \item Ctrl+Z / Ctrl+Y = undo/redo (US-06).
  \item Podwójne kliknięcie lub panel właściwości = zmiana typu / parametrów.
  \item Wskaźnik postępu / spinner na canvasie podczas długiego layoutu (>200\,ms).
\end{itemize}

Wizualizacje (makiety) zostaną doprecyzowane w kolejnej iteracji dokumentu lub w osobnym załączniku (Figma / szkice). Na obecnym etapie wystarcza opis obszarów i mapowanie na historyjki użytkownika.

\section{Zewnętrzne interfejsy}

\subsection{Format pliku projektu (JSON)}

Własny, wersjonowany format JSON (schema w osobnym pliku JSON Schema):

\begin{verbatim}
{
  "version": "1.0",
  "meta": { "title": "...", "created": "...", "seed": 12345 },
  "pattern": {
    "stitches": [ { "id": "...", "type": "dc", "parents": ["..."], "round": 2 }, ... ],
    "yarnPosition": "...",
    "currentRound": 3
  },
  "view": { "zoom": 1.0, "panX": 0, "panY": 0 }   // opcjonalnie
}
\end{verbatim}

Zachowanie 100\% danych strukturalnych (NFR-R1). Niepoprawny plik $\to$ komunikat błędu, brak awarii (NFR-R2).

\subsection{Eksport graficzny}

\begin{itemize}
  \item \textbf{SVG} -- natywny, wektorowy, zachowuje symbole jako \texttt{<g>} / \texttt{<path>}.
  \item \textbf{PNG / JPEG} -- rasteryzacja SVG przez OffscreenCanvas lub tymczasowy \texttt{<canvas>}.
  \item \textbf{PDF} -- jsPDF + svg2pdf.js lub podobna biblioteka; jedna strona A4 / Letter z dopasowanym schematem.
\end{itemize}

Brak integracji z zewnętrznymi usługami (brak OAuth, API chmurowych itp.). Standardy: SVG 1.1 / 2, JSON (RFC 8259), File API / File System Access API.

\subsection{Uzasadnienie wyboru podejścia do layoutu}

Na podstawie literatury (m.in. Greer \& Mould 2025 -- \textit{Modeling Crochet Patterns with a Force-directed Graph Layout}) oraz analizy istniejących narzędzi (CrochetPARADE, Stitch Fiddle) wybrano podejście force-directed / constraint-based. Nie tworzymy nowego algorytmu od zera; wartość inżynierska leży w integracji, dostosowaniu sił (orientacja symboli względem rodzica, preferowane proporcje H/W, minimalizacja nakładania) oraz zapewnieniu interaktywności (Web Worker, determinizm przy seedzie). Adapter bibliotek pozwala na ewentualną wymianę implementacji bez wpływu na resztę systemu.

\subsection{Środowisko deweloperskie}

Node.js + npm/pnpm, ESLint + Prettier, Git. Testy w CI (GitHub Actions). Brak zależności od konkretnego systemu operacyjnego -- rozwój możliwy na Windows / macOS / Linux. Wersje narzędzi są przypięte (\texttt{.nvmrc}, \texttt{package-lock.json} / \texttt{pnpm-lock.yaml}).
